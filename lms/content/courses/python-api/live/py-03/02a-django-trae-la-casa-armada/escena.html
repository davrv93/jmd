Teoría 1 de 4 · Django

Django te entrega la casa ya armada

  1. FastAPI te dio piezas; Django, la casa

    Con FastAPI tuviste rutas, validación y /docs; la base de datos, el panel y el login los eliges tú. Django sigue la filosofía de las «baterías incluidas»: ORM, migraciones, panel de administración y usuarios vienen en la caja.

    Son dos estilos, no uno mejor que otro: FastAPI te deja elegir cada pieza; Django ya tomó muchas decisiones por ti.

  2. Un proyecto guarda varias apps

    El proyecto es la casa: la configuración (settings.py) y las rutas principales (urls.py). Las apps son los cuartos y cada una hace una cosa. Tu inventario será una app; el panel admin y los usuarios (auth) también son apps, ya incluidas.

  3. Un pedido recorre cuatro paradas

    Llega GET /api/productos/. urls.py prueba las rutas en orden y se queda con la primera que coincide; llama a la vista; la vista pide los datos al modelo y el ORM los lee de la base. La vista devuelve la respuesta.

    Django se describe como un framework «MTV»: modelo, template y vista. En una API no hay template: responde con JSON, que arma el serializer (teoría 3).

  4. Nació con plazos de periódico

    Django salió de World Online, la web de un periódico, que construía aplicaciones «con plazos de periodismo». En otoño de 2003, Adrian Holovaty y Simon Willison dejaron PHP por Python; en el verano de 2005 publicaron el resultado como código abierto.

    Lectura nuestra, no de la fuente: si cada nota tiene hora de cierre, no hay tiempo de armar la casa cada vez.

  5. Tu inventario se muda de casa

    Lo que en FastAPI vivía en main.py se reparte: las rutas van a urls.py y views.py, la clase Producto pasa a models.py, y el dict en memoria se vuelve una tabla. Al reiniciar, el dict se vaciaba; la tabla se queda.

  6. Ahora: levanta tu proyecto

    startproject crea la casa, startapp el cuarto del inventario y runserver la abre en tu navegador. Si ves el cohete de Django, todo va bien. Lo haces en la escena siguiente.
