Teoría 2 de 4 · El ORM de Django

Una clase de Python se vuelve una tabla

  1. Escribes una clase, no SQL

    En models.py describes un producto como una clase de Python. Cada atributo será una columna, y Django agrega solo la columna id. La tabla se llamará inventario_producto: el nombre de la app, un guion bajo y el modelo en minúsculas.

    Desde Django 6.0, ese id es un BigAutoField: un entero de 64 bits que crece solo.

  2. makemigrations escribe el plan

    makemigrations compara tus modelos con las migraciones que ya existen y escribe un archivo nuevo, 0001_initial.py, con la operación CreateModel. Es un plan en Python que puedes leer y guardar en Git. La base todavía no cambia.

  3. migrate lo aplica a la base

    migrate lee el plan y lo ejecuta: crea la tabla en db.sqlite3 y anota que la 0001 ya se aplicó, para no repetirla. El SQL lo escribe Django por ti.

    Simplificado: el SQL real agrega NOT NULL, AUTOINCREMENT y un CHECK (stock >= 0). El exacto lo ves con python manage.py sqlmigrate inventario 0001.

  4. Las migraciones son el historial de tu base

    La documentación de Django lo dice así: las migraciones son un control de versiones del esquema. makemigrations empaqueta cada cambio en un archivo, como un commit, y migrate los aplica en orden. Cada archivo sabe cuál va antes que él.

  5. Tu compañera agrega el vencimiento

    En una botica, el vencimiento importa. Tu compañera agrega vencimiento al modelo, corre makemigrations y sube la 0002 al repositorio. Tú haces git pull y migrate: aparece la columna, vacía (NULL), y tus productos siguen ahí.

  6. Ahora: tu modelo y el admin

    Escribes Producto en inventario/models.py, corres las dos órdenes y creas tu usuario. Con una línea en admin.py, el panel /admin/ te deja crear, editar y borrar productos sin programar una sola pantalla.
